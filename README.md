从2.12亿Token惨案到零成本AI编程助手：我的Java与AIAgent的成长之路

我是“大数据管理与应用”专业的大一新生。这是我在自学Java与AI Agent开发过程中，踩过坑、花过冤枉钱后，摸索出的一套（零成本、低延迟、电脑不卡顿的）云端AI辅助学习最佳实践。

一、缘起：一次"2.12亿Tokens“的惨痛教训

刚开始学习Java时，我使用 ‘Codex’外接DeepSeekAPI来辅助学习。由于缺乏经验，我习惯性在同一个对话框里“无限套娃”，不断上传代码截图和历史记录。结果导致单次API请求携带了高达27万Tokens，累计消耗2.12亿Tokens！
虽说DeepSeek的定价较为便宜，但这也是一次不小的工程灾难：
“Tokens爆炸”：频繁使用截图和读取超长上下文让 API计费瞬间失控。
那么这都会导致什么后果呢？
1.模型“记忆中毒”：过长读取上下文导致AI变迟钝，回复变慢，甚至崩溃.
2.电脑发热卡顿：本人试图在本地跑6.7B的模型DeepSeek-Coder-6.7B(Ollama)时，我的16GB内存直接告急，严重影响开发体验。

二、破局：工程化思维与“外置记忆”

我开始反思，并用“软件工程”的思维去解决问题：
1. “少量使用截图提问”：改用「纯文本报错+20行左右以及最小代码块」提问。
2. “建立外置记忆”机制：本地建立「Java学习」文件夹，包括但不不限于：学习路线、易错点整理、记忆清单。当我开启新对话时，只投喂300字左右的“提炼版进度”，而不是全文。
3.实行“知识隔离”：学完“数组”立刻关闭对话框，开启新对话去学“面向对象”，不会把不同模块混在一起。

三、架构选型：从本地Ollama到云端零成本API

为了彻底摆脱"Tokens焦虑”和“电脑卡顿”等问题，我对比了本地与云端方案：
1. 本地部署尝试（失败告终）
一开始，为了避免 API 费用，我尝试本地部署 `Ollama+DeepSeek-Coder-6.7B`。
优势：完全免费，不仅彻底断网可用，而且没有速率限制。
缺陷：6.7B模型虽然小，但依然需要吃掉约4G左右的显存。加上Windows系统和IDE的开销，16GB内存瞬间“捉襟见肘”。一旦跑起来，风扇狂转，电脑发热明显，甚至连浏览器都不敢多开。这种“为了省钱而牺牲开发体验”的做法，极度影响学习效率！

2. 云端API破局（最终选择）

放弃本地部署后，我通过 `CC switch` 配置 Codex外接云端大模型。
探索过程：本人测试了DeepSeek V4.1flash(成本极低，但依旧有Token消耗)，最终锁定智谱AI的`GLM-4.7-Flash`。
  爽点：它是目前国内承诺“永久免费”的云端大模型API接口，代码能力完全覆盖“找错、写骨架、给建议”的需求。最关键的是［计算全在云端］我的电脑零压力、不发热、不卡顿。

  最终结论：
作为大一学生，我的核心诉求是“快速解决问题”而非“部署大模型本身”。放弃16GB内存硬跑本地模型，转投云端 `GLM-4.7-Flash` 至少提高了学习效率不是吗

2. 拒绝无脑截图：截图是Token杀手。遇到报错，只复制控制台的红色纯文本。
